# 传奇之路滚动数据仓库实施计划

> 2026-07-31 扩展：后续采集在一次 battlelog 请求中同时生成 `base8` 与 `full_loadout`，不增加官方请求。完整配置使用独立载荷表补全旧事实，不改变全库 `battle_id`；旧数据只参与基础口径。字段、冲突、三十范围统计、RAG 口径与零云端额度边界见 [完整配置数据契约](../FULL_LOADOUT_DATA_CONTRACT.md)。

状态：实施中
分支：`feature/rolling-pol-corpus`
默认范围：`7d_all`

## 目标

用一份 `data/corpus/corpus.sqlite` 长期事实库替代持续覆盖的巨型主 JSON。事实以稳定、双方顺序无关的 `battle_id` 全局去重，批次观察关系单独保存。业务只读取原子发布的派生快照组，不直接查询事实库。

三十个范围固定为最近 0-7 天、7-14 天前、14-21 天前、21-28 天前、28-35 天前、累计 0-35 天，分别乘以前 100、前 200、前 500、前 1000、全量。前端显式传递 `dataset_scope`；模型、自然语言解析器和 Skill 路由均不负责选择范围。

## 采集节奏

- 上海时区每天 03:00 运行一次。
- 每天都执行 `weekly_expanded`：冻结全球传奇之路前 1000 名，先抓本人，再只沿已接受传奇之路对局扩散，目标严格为 200,000 场批内唯一对局。名称中的 `weekly` 是历史兼容命名，不再表示每周一次。
- `daily_ranked` 仅保留为底层历史兼容模式，不由计划任务、默认入口或采集交接流程选择。
- 任何 429、预算耗尽、范围污染、事实冲突都会使批次失败。失败批次只保留诊断摘要，观察关系和孤立事实立即清理。
- 事实窗口按成功批次 `completed_at` 计算。扩散批次在真实 35×24 小时窗口内不设数量上限，且任何观察不超过真实 35×24 小时。

## 成本和资源边界

- 采集、规范化、去重、过期、统计、切片、哈希、审计和导出：云端模型调用 0，云端 embedding 调用 0。
- RAG 只对高密度聚合文档做本机 Ollama embedding，不对单场对局向量化。
- Qdrant 使用 `F:` 盘持久化路径和磁盘向量；BM25 按范围懒加载，最多缓存两个范围。
- 采集并发固定为 1，默认 1 请求/秒；瞬时网络错误最多低速重试 2 次。出现过一次 429 仍使批次验收失败。
- 新扩散批次预计写入后剩余空间不足 20 GiB 时拒绝启动。
- 工作区每处理一个玩家即提交 SQLite；内存只保留当前 battlelog、小批缓冲和有界排行榜队列。

## 发布合同

每次成功入库或窗口过期后顺序生成三十个范围的结构化统计和聚合 RAG 文档。结构化库同时物化基础卡、实际出现的普通/觉醒/精英实体和塔楼；相邻七天窗口另生成带 Wilson 95% 区间和样本门槛的 `meta_delta`。每份文档包含快照组、范围、窗口、唯一对局数和批次组成。Qdrant 检索强制过滤 `metadata.dataset_scope`，并按 `entity_mode`/`deck_mode` 限制证据口径。

完整配置能力必须同时报告 `complete_loadout_ready` 和 `entity_stats_ready`。前者证明合法载荷存在，后者证明统一实体统计已完成物化；旧组只有前者时前端保持置灰，不允许回退到基础八卡。业务 RAG 的数值校验失败修复是本地确定性过滤，不发起重试模型调用，不改变采集与发布的零云端模型成本边界。

所有非空范围的结构化统计、文档验证、指纹对齐和检索探针全部通过后，才原子替换 `data/active_snapshot_group.json`。尚无批次的历史分段发布明确空态，不伪造实体或趋势证据。任一可发布范围失败时旧快照组继续服务。派生快照组只保留当前和上一个完整版本。

采集与后处理使用同一个跨进程写锁。`8091` 在首个完整三十范围快照组发布前继续服务旧快照，旧 JSON 和索引不删除、不覆盖。旧十范围快照组仍可读取已有范围，但新增历史分段和实体统计保持未就绪，绝不自动回退。成功发布并完成业务验收后，精确删除本批 `data/rolling_work/<batch_id>`，避免重复保留采集阶段 SQLite 和 JSONL；事实库、当前/上一代快照组和失败待续传工作区不得删除。
